# Build and run

English | [한국어](build.ko.md)

How to build on each OS with CMake or the Visual Studio solution, and how to run the server, the clients
and the tests. What the targets are is in `docs/architecture.md`.

**Both build systems are maintained**, the CMake presets and the hand-maintained Visual Studio solution. Every change
that affects the build goes into both (`CLAUDE.md` "규칙", Korean only).

## Build

Requirements: CMake 3.21+, Ninja, a C++20 compiler (MSVC 2022+, GCC 11+, Clang 14+).

The CMake minimum is fixed at 3.21 so that Ubuntu 22.04 LTS's stock CMake (3.22) can build it.
Features from 3.25 on (`add_subdirectory(... SYSTEM)`, preset schema 4+) are not used.

```
git submodule update --init
cmake --preset windows-msvc        # or linux / macos
cmake --build --preset windows-msvc
ctest --preset windows-msvc
```

- Output: `build/<preset>/bin/`.
- Single test: `ctest --preset windows-msvc -R smoke_test --output-on-failure`.
- The first build compiles protobuf and protoc from source: about 180 targets, a few extra minutes.
- The protobuf `cmake_minimum_required` deprecation warning under CMake 4 is harmless.

### Windows (CMake)

The Ninja preset needs the VS developer environment. From a plain PowerShell:

```
cmd /c "call ""C:\Program Files\Microsoft Visual Studio\18\Community\VC\Auxiliary\Build\vcvars64.bat"" >nul 2>&1 && cmake --preset windows-msvc && cmake --build --preset windows-msvc && ctest --preset windows-msvc"
```

- A PC with only VS 2022: `...\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat`.
- Calling it through git bash's `cmd //c` fails silently. Use PowerShell.

### Linux (verified on WSL2)

WSL2 Ubuntu 22.04 (g++ 11.4, CMake 3.22, Ninja 1.10). The `linux` preset builds with zero warnings and all
four tests pass.

```
rsync -a --delete --exclude .git --exclude .vs --exclude build \
      --exclude third_party/_install --exclude third_party/_build /mnt/<drive>/<repo>/ ~/strandwire/
cd ~/strandwire && cmake --preset linux && cmake --build --preset linux && ctest --preset linux
```

- Building directly on `/mnt/<drive>` (the Windows file system) is very slow. Copy into the WSL home first.
- `.vs` is locked by Visual Studio; exclude it from the copy.
- Calling WSL from PowerShell mangles `$` variables and quotes. Put the script in a file and run
  `wsl.exe -d Ubuntu -- bash /mnt/c/.../script.sh`.
- `sudo` needs a password and cannot be automated. The user installs packages themselves.
- A server inside WSL2 is reachable from Windows at `127.0.0.1:<port>`. Use that for cross-connection checks.

### macOS (verified over SSH)

A clone on a Mac on the LAN (`<user>@<mac-host>`, key authentication). The `macos` preset builds with zero
warnings and all four tests pass.

```
tr -d '\r' < script.sh | ssh -o BatchMode=yes <user>@<mac-host> 'bash -s'
# inside script.sh:
cd <repo>
export PATH="/opt/homebrew/bin:$PATH"
git submodule update --init --depth 1
cmake --preset macos && cmake --build --preset macos && ctest --preset macos
```

- The Mac repository is a GitHub clone. **The commit under test must be pushed to origin first.**
- Non-interactive SSH shells have no Homebrew on PATH. Prepend `/opt/homebrew/bin` in the script.
- Send scripts as files through standard input. Strip CRs from files created on Windows.
- The Mac's firewall is off, so a listening server pops no permission dialog.
  If it were on, warn the user before running the server or `smoke_test`.
- Cross-connection: from Windows, `DummyClient --ip <mac-host>`.

### Visual Studio solution (Windows, hand-maintained)

Day-to-day Windows development uses `strandwire.sln` at the root. It is maintained by hand, not generated by CMake.

- 9 projects: `LogLib`, `ProtoLib`, `ServerLib`, `NetworkServer`, `NetworkClient`, `DummyClient`,
  `wire_test`, `smoke_test`, `app_test`.
- Configurations `Debug|x64` / `Release|x64`, toolset v143.
- The vcxproj files sit in their source folders. Output: `build\vs\<Configuration>\bin\`.

**On a new PC, install protobuf once first.** Run it again after changing the protobuf submodule version.

```
powershell -ExecutionPolicy Bypass -File tools\build_protobuf.ps1
& "C:\Program Files\Microsoft Visual Studio\2022\Community\MSBuild\Current\Bin\MSBuild.exe" strandwire.sln /m /p:Configuration=Debug /p:Platform=x64
.\build\vs\Debug\bin\smoke_test.exe
```

protobuf:

- The solution does not build protobuf; it links the installed output.
- The script installs Debug and Release into `third_party\_install\protobuf\<Configuration>\`
  (`bin\protoc.exe`, `lib\libprotobuf(d).lib`, `include\`).
- Without the install, the `ProtoLib` build fails with a message to run the script.
- The install folder and `third_party\_build\` are gitignored.

Settings:

- Shared settings live in two props files. Keep the values equal to the root `CMakeLists.txt`.
  - `strandwire.config.props` - toolset, character set, debug runtime. Imported before `Microsoft.Cpp.props`.
  - `strandwire.props` - include paths, preprocessor definitions, C++20, `/W4 /utf-8`, output directories,
    protobuf paths and linking.
- No compiler options in individual vcxproj files; edit the props.
  The one exception is `ProtoLib.vcxproj`, which disables warnings for generated code.
- protobuf headers, the generated-code folder and `third_party\spdlog\include` are on `ExternalIncludePath`,
  excluded from `/W4` warnings.
- Paths are relative to the props file, not `$(SolutionDir)`, so a vcxproj builds on its own.
- No precompiled headers.

References:

- spdlog is header-only, so there is no prebuild step. Only `LogLib\logger.cpp` includes it.
- Executables that log reference `LogLib` directly; executables that use `ProtoLib` reference it directly.
- `ServerLib`'s reference to `ProtoLib` is for build order only (`LinkLibraryDependencies=false`); the libs are not merged.

Adding or removing a source file touches three places (`CMakeLists.txt`, `.vcxproj`, `.vcxproj.filters`); the CTest
`check_vs_sync` fails on drift. The procedure is in `CLAUDE.md` "변경 절차" (Korean only).

## Run

```
.\build\windows-msvc\bin\NetworkServer.exe [--ip 0.0.0.0] [--sid 0.0.11.1] [--config lobby_config.json]
.\build\windows-msvc\bin\NetworkClient.exe 127.0.0.1 10000 <name>     # a line = one chat message, quit = exit
.\build\windows-msvc\bin\DummyClient.exe --ip 127.0.0.1 --port 10000 --session 100 --duration 10
```

- The server's port, threads, timeout and log settings come from the `--config` file
  (`docs/architecture.md`, "NetworkServer").
  Without a file it listens on port 10000 with one worker per CPU core.
- Options of the two clients:
  - `--log-level trace|debug|info|warn|error|fatal|off` (default info).
  - `--log-dir <folder>` (default none = console only).
- The server stops cleanly on ESC or Ctrl+C in the console.
- DummyClient's per-session `LOGIN OK` is at debug level and hidden by default.
- DummyClient exits after `--duration` seconds; exit code 0 when every session logged in.
- To pipe stdin into NetworkClient use git bash:
  `(sleep 1; echo hello; sleep 1; echo quit) | ./NetworkClient.exe 127.0.0.1 10000 alice`.
  PowerShell 5.1 script-block pipes do not reach a native process's stdin in time and hang.
